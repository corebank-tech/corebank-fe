# CoreBank 관리자 채널 요구사항 정의서 — 2차 확정 범위

- 작성 2026-09-22 · 갱신 2026-09-23 · 김다연(P3) · 이슈 #156 · #159
- 범위 정본: `corebank-server` 의 `docs/phase2/` — `README.md`(공통 규칙 · 결정 로그 · 범위 밖) · `tasks.md`(태스크별 범위 · 완료 기준)
- **v3 판본(`plans/260916-corebank-phase2-v3/`)은 폐기됐다**(최종안 D-21). 이 문서가 그 경로를 인용하던 것을 2026-09-23에 전부 갈아끼웠다
- 고객 채널 요구사항 정의서: `corebank-design/docs/requirements.md`(원본 `CoreBank_요구사항정의서_v1_4.xlsx`)

## 0. 이 문서가 왜 있나

1차 요구사항 정의서에 **관리자 화면은 0건**이다. "관리자"는 세 번 나오는데 전부 고객 요구사항 안의 언급이다(POL-004 "계정 잠금 해제 방식 = 관리자 수동, 고객용 해제 화면 미제공" 등).

작성 시점(9/22)의 2차 계획에 있던 것은 **담당표**였다 — 누가 언제 만드는지는 있으나 무엇을 만족해야 완료인지가 없었다. 9/23 최종안이 `tasks.md`에 태스크별 범위·완료 기준을 넣어 그 공백을 줄였지만, **관리자 화면의 요구사항·정책값은 여전히 이 문서가 정본이다**(최종안 README §3-7). 그 공백의 비용은 이미 나타났다. ADM-02는 조회기간 기본값·상한의 근거가 없어 고객 규정(POL-021)을 쓸 수 없었고, `PeriodField` 기본값을 빌려 쓴 뒤 그 사정을 코드 주석으로 남겼다(`src/pages/admin/adm02-trial-balance.tsx:80-83`, `:134-137`).

이 문서는 **2차 확정 범위에 한해** 화면ID·권한·정책값·인수기준을 고정한다. 범위를 넓히지 않는다 — 최종안이 범위 밖으로 판정한 것은 §5에 사유만 적는다.

**상태 표기**

| 표기 | 뜻 |
|---|---|
| 확정 | 계획 문서 또는 구현에 근거가 있다. 출처를 함께 적는다 |
| 제안 | 이 문서에서 처음 정한다. 이의가 없으면 확정으로 본다 |
| 미정 | 타 트랙(주로 P1)의 결정을 기다린다 |

## 2. 권한 매트릭스

### 2-1. 권한 집합

2차 확정 계약의 **고정 5종**이다(최종안 README §3-4). FE는 늘릴 수 없다.

| 권한 | 화면 표기 | 뜻 |
|---|---|---|
| `GL_READ` | 회계 조회 | 원장·시산표 조회 |
| `GL_WRITE` | 회계 변경 | 결산·역분개 — **2차에 쓰는 화면이 없다**(#129 범위 밖) |
| `CUSTOMER_READ` | 고객 조회 | 고객 검색·상세 |
| `CUSTOMER_WRITE` | 고객 변경 | 잠금 해제·비밀번호 초기화·상태 변경 |
| `AUDIT_READ` | 감사 조회 | 감사 성격 조회 — **현재 이 권한을 검사하는 코드가 없다** |

구현: `src/shared/types/admin-permission.ts:17-25`(이름 집합) · `src/entities/auth/lib/session-role.ts`(판정 단일 출처).

### 2-2. 화면 × 권한

| 화면 | 진입 | 조회 | 변경 | 근거 |
|---|---|---|---|---|
| ADM-90 셸 | `role = ADMIN` | — | — | `src/app/require-admin.tsx:38` |
| 관리자 홈 | `role = ADMIN` | 권한 조건 없음 | — | `src/shared/config/admin-nav.ts:28` |
| ADM-01 | `CUSTOMER_READ` | `CUSTOMER_READ` | `CUSTOMER_WRITE` | `admin-nav.ts:38` · `adm01-customer-detail.tsx:78` |
| ADM-02 | `GL_READ` | `GL_READ` | 없음(조회 전용) | `admin-nav.ts:50` |
| ADM-03 | `GL_READ` | `GL_READ` | 없음(조회 전용) | D-09 |
| ADM-04 | `AUDIT_READ` | 동 | 없음(조회 전용) | D-04 · tasks.md `FE ADM-04` |

**ADM-03에 딱 맞는 권한이 고정 5종에 없었다.** 정보계 대시보드는 회계(GL)도 고객(CUSTOMER)도 감사(AUDIT)도 아니다. FE가 세 안(`GL_READ` 대용 / 권한 조건 없음 / 6번째 권한 신설)을 올렸고, **최종안 D-09가 `GL_READ`로 확정**했다 — 권한 집합 5종은 늘리지 않는다. 서버 PH-77도 같은 권한을 쓴다.

### 2-3. 권한이 작동하는 지점 — 3단

1. **메뉴 미표시** — `visibleAdminNav()`가 권한 없는 항목을 거르고 빈 그룹을 제거한다(`src/widgets/admin-shell/visible-nav.ts:14-27`).
2. **화면 진입 차단** — `RequirePermission`이 라우트의 화면을 감싸, 주소창으로 직접 들어와도 권한이 없으면 화면 대신 안내를 그린다(`src/app/require-permission.tsx`, 배선은 `src/app/routes/admin-routes.tsx`의 `guardedLazy`).
3. **변경 버튼 미표시** — 권한이 없으면 버튼을 비활성화하지 않고 영역 전체를 안내로 갈아끼운다(`adm01-customer-detail.tsx:248, :278-283`).

2단은 #156에서 추가했다. 그 전에는 메뉴와 버튼만 막아, `CUSTOMER_READ`가 없는 관리자가 `/admin/customers`를 주소창에 직접 치면 고객 목록이 그대로 그려졌다.

**세 단은 서로를 대신하지 못한다.** 1단만으로는 주소창 접근을 막지 못하고, 2단만으로는 한 화면 안의 변경 권한을 가르지 못한다. 그리고 **셋 다 서버 인가를 대신하지 않는다** — 화면 가드는 권한 없는 사용자가 버튼을 누르기 전에 막는 한 겹이고, 거부의 최종 책임은 서버에 있다.

가드는 셸 **안쪽**에 선다. 막힌 화면에서도 네비가 남아야 관리자가 자기가 볼 수 있는 다른 화면으로 옮겨갈 수 있다.

## 부록 A. Apache Fineract 운영 콘솔 대조

관리자 채널의 표준 구성과 우리 범위의 차이를 확인하기 위해 Apache Fineract 공식 운영 콘솔(`openMF/web-app`)의 모듈 구조를 조사했다(2026-09-22 기준 `master`).

최상위 30개 모듈 중 관리자 축은 넷이다.

| Fineract 모듈 | 하위 화면(발췌) | 우리 대응 | 판정 |
|---|---|---|---|
| `accounting` | `chart-of-accounts` · `create-journal-entry` · `search-journal-entry` · `migrate-opening-balances` | 계정과목·전표·분개·개시잔액 — BE(PH-20·21)만 있고 화면 없음 | 범위 밖 (REQ-ADM-025) |
| `accounting` | `closing-entries` · `revert-transaction` | 결산·역분개 (#129) | EX-A01 |
| `accounting` | `accounting-rules` · `financial-activity-mappings` · `frequent-postings` · `periodic-accruals` · `provisioning-entries` | 대응 없음 | 2차 대상 아님 |
| `system` | `roles-and-permissions` | 권한 부여·회수 | EX-A02 |
| `system` | `audit-trails` | 감사로그 조회 | EX-A04 |
| `system` | `configure-maker-checker-tasks` | 승인 대상 지정 | EX-A11 |
| `system` | `manage-jobs` | 배치 실행 현황 (#132) | EX-A09 |
| `organization` | `holidays` · `working-days` | 영업일·휴일 관리 (#132) | EX-A09 |
| `organization` | `offices` · `employees` · `tellers` · `currencies` | 단일 조직·단일 통화라 해당 없음 | 대상 아님 |
| `users` | `create-user` · `edit-user` · `view-user` | 관리자 계정 관리 | EX-A10 |
| `tasks` | 승인 대기함 | maker-checker 대기함 | EX-A11 |
| `clients` | 고객 조회·상세 | **ADM-01** | 구현 |
| `reports` | 운영 리포트 | **ADM-02 · ADM-03** | 구현·예정 |

세 가지를 확인했다.

1. **관리자 계정(`users`)과 고객(`clients`)은 다른 모듈이다.** 우리 ADM-01 "고객 계정 운영"은 Fineract 기준 `clients` 쪽이고, `users`에 해당하는 화면은 우리에게 없다 — 빠뜨린 것이 아니라 제외한 것이다(EX-A10).
2. **승인 대기함과 감사로그가 일급 화면이다.** 금전적 영향이 있는 변경은 2인 승인, 조회 이력은 별도 화면이 표준이다. 우리는 둘 다 없고(EX-A11·A04), 그래서 ADM-01의 세 변경 액션은 **단독 실행·기록 없음**이다. 2차 범위 판단으로는 유효하나, 이 한계는 회계 통제 리포트에 명시한다.
3. **`accounting`에 시산표가 없다.** 장부를 바꾸는 화면(`accounting`)과 읽어서 보여주는 화면(`reports`)이 갈려 있다. 우리 ADM-02·ADM-03도 둘 다 후자이므로 관리자 네비에서 같은 축으로 묶는다.
